Decided Status is a history, not a field

Each change appends a dated row. A single mutable status column would erase the thing you actually want later: how long each stage took, and where applications die.

Decided Bars stack in outcome order

Rejected at the base, then Applied, Screening, Interview, Offer rising. This exact order was validated for colour-blind separation — reordering the stack breaks that, so it is not a free choice.

Needs a call Files, or pasted text?

Uploading the real PDF is truer documentation but means Supabase Storage, a bucket policy, and size limits. Pasted text is free and searchable. I would ship pasted text first and add upload after — though the résumé is the one where the file itself matters.

Where the data comes from

Six surfaces already log token spend. Three — Cases, Case Lab and Code drills — spend nothing, so today they are invisible. activity_events is what makes their calendars real rather than permanently empty.

Decided One event per surface per day

A chat with forty messages is one day of using Ask Hugh, not forty. Events deduplicate at write time, so the calendar answers “did I show up” rather than “how chatty was I”.

Decided Separate from usage_logs

usage_logs exists to price tokens and enforce quota; that is a billing record and should stay one. Overloading it with page views would corrupt the cost maths migration 036 just got right.

Needs a call The red badges are honest, but ugly

I marked which surfaces are not yet instrumented. Ship with those calendars visibly empty and labelled, or instrument all nine first and launch complete? I would instrument first — a view whose main content is “coming soon” teaches nothing.

Before I build

Four things I could not settle from the brief. Everything else I will take as approved.

1

Three tabs, or three routes?

Drawn here as tabs under one /monitor shell. That keeps one home card and one mental model, but the panes get tight — Applications is already three columns.

I would keep tabs, with Applications able to open a full-width detail view the way /notes does.

2

Monitor needs the Notes scroll exception

Hugh's rule is no scroll on any screen. Six skills fit; forty applications do not, and neither does a year of diary entries. Monitor is a records tool, like Notes.

I would grant it the same exception Notes has: page locked to the viewport, panes scroll internally. That is an edit to the architecture rules in CLAUDE.md, so it is yours to approve.

3

Does Applications belong in Hugh at all?

Skills and Usage are about learning. A job-application tracker is career admin — useful, personal, and the first thing in Hugh with no connection to data and analytics. The topic gate exists precisely to stop that kind of drift.

I will build it as asked. Flagging it once because it is the piece that changes what Hugh is, and you may want it gated to your own account rather than shipped to every learner.

4

What fills the Systems slot on /home?

I removed that card, so the grid is five. Monitor can take the empty slot with the cyan accent shown throughout here.

Confirm Monitor takes the sixth slot and I will wire the card in the same pass.
